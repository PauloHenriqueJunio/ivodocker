ROTEIRO DE APRESENTAÇÃO — Foco em CI/CD, HELM e ARGO CD

OBJETIVO
Explicar em profundidade como o projeto está estruturado para GitOps com Helm + Argo CD e como o CI/CD no GitHub Actions constrói, versiona e promove imagens no GHCR atualizando os arquivos de values por ambiente. Também cobre práticas para evitar loops de pipeline, gestão de namespaces, ordem de sincronização (sync waves), segredos e troubleshooting.

ARQUIVOS-CHAVE DE CI/CD E GITOPS

1) .github/workflows/ci-cd.yaml (Pipeline GitHub Actions)
Propósito: construir a imagem da aplicação, publicar no GitHub Container Registry (GHCR) e atualizar os arquivos de Helm com a nova tag de imagem, mantendo Git como fonte da verdade para o Argo CD.

Disparo (on):
- push na branch "teste-argo-cd" (pipeline de desenvolvimento). Recomenda-se duplicar/parametrizar para produção em "main" quando desejar promover releases.

Permissões (permissions):
- contents: write — permite commitar de volta no repositório (atualizar values files).
- packages: write — permite publicar imagens no GHCR.

Autenticação e checkout:
- actions/checkout@v4 com token "secrets.TOKEN_IVO" para permitir push de volta (pode-se usar GITHUB_TOKEN se a organização permitir contents:write para Actions).
- docker/login-action@v3 com username = repo owner e password = GITHUB_TOKEN (packages:write habilitado nas permissões do workflow/repósito).

Build multi-plataforma (opcional, mas configurado):
- setup-qemu e setup-buildx — infraestrutura para builds consistentes, inclusive cross-arch. Mesmo sem múltiplas plataformas habilitadas, manter Buildx é saudável.

Versionamento da imagem:
- tag = primeiros 7 chars de GITHUB_SHA (imutável, evita "latest").
- repository = ghcr.io/<owner>/<repo> convertido para minúsculas (requisito do GHCR).

Publicação da imagem:
- docker/build-push-action@v5 com push: true e tags: ghcr.io/<repo>:<sha7>.

Atualização dos values do Helm (ponto crítico):
- O workflow atualiza, via sed, os campos "image.repository" e "image.tag" nos três arquivos:
  - helm/ivodocker-chart/values.yaml
  - helm/ivodocker-chart/values-dev.yaml
  - helm/ivodocker-chart/values-prod.yaml
- Isso garante que cada ambiente aponte para a mesma imagem recém-publicada (ou, se preferir, pode-se atualizar apenas o values do ambiente correspondente ao gatilho — prática comum para evitar cross-env updates).

Commit e push automatizados:
- Configura user/email do bot, adiciona os três arquivos, commita com mensagem contendo [skip ci] e faz push.
- Proteção contra loop: o job tem if: "!contains(github.event.head_commit.message, '[skip ci]')", evitando re-execução quando a alteração foi feita pelo próprio bot.

Melhorias recomendadas (evitar loops e garantir previsibilidade):
- Adicionar condição extra: if: github.actor != 'github-actions[bot]'.
- Usar concurrency para impedir execuções concorrentes na mesma branch:
  concurrency:
    group: ${{ github.workflow }}-${{ github.ref }}
    cancel-in-progress: true
- Separar pipelines por branch: um workflow dedicado para main (prod) que só atualiza values-prod.yaml; outro para teste-argo-cd (dev) que só atualiza values-dev.yaml.
- Usar path filters (paths) se quiser disparar apenas quando arquivos de aplicação mudarem (cuidado para não bloquear o commit do próprio bot quando atualizar values).

Requisitos de secrets e tokens:
- secrets.TOKEN_IVO: token com repo:write para permitir commit/push (alternativamente, GITHUB_TOKEN com permissões adequadas pode bastar).
- GITHUB_TOKEN precisa de packages:write para publicar no GHCR (ver permissões do workflow e configurações do repositório/organização).

2) helm/ivodocker-chart (Chart Helm)
Finalidade: empacotar manifestos Kubernetes parametrizados. Utilizado pelo Argo CD (source.type=Helm) para renderizar e aplicar.

Arquivos de valores (parametrização por ambiente):
- values.yaml — baseline (também atualizado pelo CI).
- values-dev.yaml — overrides para DEV (apontado pelo Application dev). "image.tag" é atualizado pelo CI.
- values-prod.yaml — overrides para PROD (apontado pelo Application prod). "image.tag" é atualizado pelo CI.

Templates relevantes:
- templates/secret.yaml — gera Secret Opaque com credenciais DB_*, obtidas de .Values.database.* (renderizadas em base64). Para produção real, preferir External Secrets e providers (Vault/AKV).
- templates/job-migrations.yaml — Job de migrações com annotation argocd.argoproj.io/sync-wave: "1". Executa antes do Deployment, usando a mesma imagem e credenciais via envFrom Secret. Se a imagem referenciada pela tag não existir no registry, ficará em ErrImagePull/ImagePullBackOff e bloqueará a onda seguinte (desejado, pois evita subir app sem schema).
- templates/deployment.yaml — Deployment com argocd.argoproj.io/sync-wave: "2". Só aplica depois que o Job (wave 1) estiver saudável. Injeta variáveis via envFrom Secret e expõe porta conforme .Values.service.port.
- templates/service.yaml — Service ClusterIP da aplicação.

Boas práticas de chart aplicadas:
- Tags imutáveis em image.tag (evita drift e comportamentos não determinísticos).
- Separação de values por ambiente para GitOps claro (dev vs prod).
- Uso de sync waves para orquestrar migrações antes de subir a aplicação.

3) argocd-gitops/* (Applications Argo CD)
Finalidade: declarar o estado desejado dos ambientes via CRD Application.

dev/application.yaml (ambiente DEV):
- source.repoURL: https://github.com/PauloHenriqueJunio/ivodocker
- source.targetRevision: teste-argo-cd (branch DEV)
- source.path: helm/ivodocker-chart
- source.helm.valueFiles: [values-dev.yaml]
- destination.server: https://kubernetes.default.svc
- destination.namespace: dev (deve existir; opcional: annotation CreateNamespace=true)
- syncPolicy.automated: prune: true, selfHeal: true

prod/application.yaml (ambiente PROD):
- source.targetRevision: main (branch de produção)
- source.helm.valueFiles: [values-prod.yaml]
- destination.namespace: prod
- Política de sync análoga à DEV.

operator/application-mysql-operator.yaml (operador de banco):
- Instala o MySQL Operator a partir do repositório oficial (path pode variar por versão). Após o operador, é necessário aplicar um CR (Custom Resource) para criar a instância do banco e expor um Service cujo hostname deve casar com .Values.database.host do chart.

FLUXO CI/CD + GITOPS (DETALHADO)
1) Dev faz push em "teste-argo-cd" → aciona workflow.
2) Workflow constrói imagem com tag = SHA curto, faz push no GHCR.
3) Workflow atualiza values-dev.yaml (e os demais, conforme configurado) com repository/tag e commita com [skip ci].
4) Argo CD detecta mudança no Git e reconcilia a Application DEV:
   - Aplica Secret → aplica Service → cria Job (wave 1) → aguarda sucesso → aplica Deployment (wave 2).
5) Se o Job falhar por ErrImagePull, verifique se a tag publicada existe no GHCR e se a imagem é pública (ou configure imagePullSecrets no chart/cluster para imagens privadas).

EVITANDO LOOPS DE CI/CD
- Use [skip ci] no commit do bot e um if no job que ignore esses commits (já implementado). Reforço sugerido:
  if: github.actor != 'github-actions[bot]'
- Separe os pipelines por branch/ambiente e atualize apenas o values correspondente (reduz alterações desnecessárias em outros envs).
- Considere workflow_run (pipeline 2 só roda após concluir o build do pipeline 1), evitando que o commit de atualização re-dispare builds.
- Utilize concurrency para evitar corridas de atualização dos values.

PERMISSÕES, TOKENS E REGISTRY (GHCR)
- GHCR exige nome totalmente minúsculo (o workflow já normaliza via tr). Se falhar com 404/401, confira:
  - Permissões do GITHUB_TOKEN (packages:write habilitado) e do repositório.
  - Visibilidade do pacote (público/privado). Se a imagem for privada, adicione imagePullSecrets no chart e um Secret dockerconfigjson no namespace (linkado em .Values.imagePullSecrets).
- TOKEN_IVO: se usado no checkout para push, precisa de repo:write. Alternativa: usar somente GITHUB_TOKEN (mais simples) se as políticas permitirem.

IMAGENS PRIVADAS (imagePullSecrets) — EXEMPLOS
Se o pacote no GHCR for privado, crie um Secret docker-registry no namespace do deploy e referencie-o no chart via .Values.imagePullSecrets.

1) Criar o Secret (namespace dev como exemplo):
kubectl create secret docker-registry ghcr-creds \
   --docker-server=ghcr.io \
   --docker-username="<seu-usuario-github>" \
   --docker-password="<seu-GITHUB_TOKEN-ou-PAT>" \
   -n dev

2) Referenciar no Helm values (o chart já suporta imagePullSecrets no Deployment):
values-dev.yaml
image:
   repository: ghcr.io/<owner>/<repo>
   tag: "<sha>"
   pullPolicy: IfNotPresent
imagePullSecrets:
   - name: ghcr-creds

values-prod.yaml (análogamente, em prod):
imagePullSecrets:
   - name: ghcr-creds

Observações:
- O Secret deve existir em cada namespace destino (dev, prod, etc.).
- Se usar PAT (token pessoal), dê escopo para leitura de packages: read:packages.
- Para organizações privadas, confira políticas de acesso ao GHCR (visibilidade e permissões).

CRIAÇÃO AUTOMÁTICA DE NAMESPACE PELO ARGO CD — EXEMPLO
Você pode instruir o Argo CD a criar o namespace de destino caso ele não exista usando a annotation CreateNamespace=true no objeto Application.

dev/application.yaml (trecho):
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
   name: ivodocker-dev
   namespace: argocd
   annotations:
      argocd.argoproj.io/sync-options: CreateNamespace=true
spec:
   destination:
      server: https://kubernetes.default.svc
      namespace: dev
   source:
      repoURL: https://github.com/<owner>/ivodocker
      targetRevision: teste-argo-cd
      path: helm/ivodocker-chart
      helm:
         valueFiles:
            - values-dev.yaml

prod/application.yaml (análogamente, com namespace prod):
metadata:
   annotations:
      argocd.argoproj.io/sync-options: CreateNamespace=true

Observações:
- Útil em clusters efêmeros/lab. Em produção, muitas equipes preferem gerenciar namespaces por IaC separado (ex.: Kustomize/Helm infra) para maior controle de RBAC/quotas.

NAMESPACES E SINCRONIZAÇÃO
- Os namespaces dev e prod devem existir ou a Application pode ter:
  metadata.annotations:
    argocd.argoproj.io/sync-options: CreateNamespace=true
- Sem o namespace, a sync falha com "namespaces \"<ns>\" not found".

MIGRAÇÕES ANTES DO DEPLOY (SYNC WAVES)
- O Job (wave 1) deve usar a mesma tag que acabou de ser publicada; caso contrário, o cluster exibirá ImagePullBackOff. Isso é desejável (falha rápida) pois impede subir a app com schema desatualizado.
- Após o Job completar (Succeeded), o Argo CD libera o Deployment (wave 2). Se o Deployment tiver readiness/liveness probes, a app só ficará Healthy quando atender as checagens.

TROUBLESHOOTING (PASSO A PASSO)
1) Application DEV OutOfSync + Missing:
   - kubectl get ns → confirme que "dev" existe.
   - Se não existir, crie (kubectl create ns dev) ou use CreateNamespace=true na Application.
2) ImagePullBackOff no Job de migrações:
   - Verifique a tag em values-dev.yaml e se a imagem existe no GHCR.
   - Confirme se o workflow realmente atualizou o values-dev.yaml (git show origin/teste-argo-cd:helm/.../values-dev.yaml).
   - Se imagem privada: configure imagePullSecrets e referencie em .Values.imagePullSecrets.
3) Loop do workflow:
   - Confirme presença de [skip ci] e if no job; adicione condição por actor e concurrency se necessário.
4) Operador MySQL não instala/progride:
   - Confirme path/branch corretos do chart/manifests do operador.
   - Verifique CRDs e logs dos pods do operador.
5) Argo CD UI/CLI:
   - Port-forward: kubectl port-forward svc/argocd-server -n argocd 8080:443
   - Login CLI: argocd login localhost:8080 --insecure --username admin --password '<senha>'
   - Sync app: argocd app sync ivodocker-dev; status: argocd app get ivodocker-dev

CHECKLIST DE ENTREGA (CI/CD + GITOPS)
- [ ] Workflow publica imagem no GHCR com tag imutável (SHA curto) e sucesso.
- [ ] Workflow atualiza os values do ambiente correto (dev/prod) com repository/tag e faz commit com proteção anti-loop.
- [ ] Argo CD Applications: dev → branch teste-argo-cd + values-dev.yaml; prod → branch main + values-prod.yaml.
- [ ] Namespaces dev/prod existentes (ou CreateNamespace=true nas Applications).
- [ ] Job de migrações (wave 1) roda e completa antes do Deployment (wave 2).
- [ ] (Se necessário) imagePullSecrets configurado para imagens privadas.
- [ ] Operador do banco instalado e CR de instância aplicado (Service apontando para o host usado em .Values.database.host).
